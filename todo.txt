Ci sono alcune vulnerabilità:

🔴 argv[1] senza controllo
c
int main(int argc, char **argv){
    // ...
    ht_load(db, argv[1]);  // ❌ se argv[1] non esiste → crash
    ht_destroy(db, argv[1]);
Fix:

c
if(argc < 2) {
    fprintf(stderr, "Usage: %s <persistence_file>\n", argv[0]);
    exit(EXIT_FAILURE);
}
🔴 read senza controllo sul valore di ritorno
c
read(newSocketFd, requestBuffer, BUFFER_SIZE);
Se read ritorna -1 o 0, requestBuffer contiene garbage o è vuoto e viene passato a handle_request comunque.

Fix:

c
ssize_t bytesRead = read(newSocketFd, requestBuffer, BUFFER_SIZE - 1);
if(bytesRead <= 0) { close(newSocketFd); continue; }
requestBuffer[bytesRead] = '\0';
🟠 sprintf in send_response può overflow
c
char fullResponseBuffer[BUFFER_SIZE + 512];
int len = sprintf(fullResponseBuffer, "HTTP/1.1 %d %s\r\n...", ...);
Se responseMsg è vicino a BUFFER_SIZE, gli header aggiuntivi (~512) possono sforare. Meglio snprintf:

c
int len = snprintf(fullResponseBuffer, sizeof(fullResponseBuffer), "HTTP/1.1 %d %s\r\n...", ...);
🟡 printf in handle_sigint
c
void handle_sigint(int sig) {
    printf("ctrl+c\n");  // ⚠️ printf non è async-signal-safe
    keep_running = 0;
}
printf non è sicuro dentro un signal handler. Fix: rimuovere il printf, o usare write(STDOUT_FILENO, "ctrl+c\n", 7).

🟡 Server single-threaded
c
newSocketFd = accept(...);
read(newSocketFd, ...);
handle_request(...);
send_response(...);
close(newSocketFd);
Una richiesta lenta blocca tutte le altre. Non è una vulnerabilità di sicurezza ma un vettore di DoS — un client che si connette e non invia dati blocca il server indefinitamente per via della read bloccante.

Fix minimo: setsockopt con SO_RCVTIMEO:

c
struct timeval timeout = {5, 0};  // 5 secondi
setsockopt(newSocketFd, SOL_SOCKET, SO_RCVTIMEO, &timeout, sizeof(timeout));
